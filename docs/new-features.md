# قابلیت‌های جدید نسخه ۲ — پیوست‌ها، خروجی اکسل رسمی و واحد واقعی کالا

> **اصل Zero Regression رعایت شده است:** هیچ جدول، ستون یا رکورد قبلی تغییر، حذف یا بازنویسی نشده؛
> تمام تغییرات **افزایشی (Additive)** و **Backward Compatible** هستند.

---

## ۱. تغییرات دیتابیس (Non-Destructive Migration)

تنها یک جدول جدید ساخته می‌شود — جداول و داده‌های موجود دست نمی‌خورند:

```sql
CREATE TABLE IF NOT EXISTS attachments (
  id                 INTEGER PRIMARY KEY AUTOINCREMENT,
  entity_type        TEXT NOT NULL CHECK (entity_type IN ('invoice','payment')),
  entity_id          INTEGER NOT NULL,
  original_file_name TEXT NOT NULL DEFAULT '',
  stored_file_name   TEXT NOT NULL DEFAULT '',
  file_path          TEXT NOT NULL DEFAULT '',
  file_extension     TEXT NOT NULL DEFAULT '',
  file_size          INTEGER NOT NULL DEFAULT 0,
  created_at         TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);
CREATE INDEX IF NOT EXISTS idx_attachments_entity ON attachments(entity_type, entity_id);
```

به‌علاوه یک ردیف تنظیمات جدید (`documents_path` با مقدار پیش‌فرض خالی) به جدول `settings`
اضافه می‌شود (فقط اگر از قبل نباشد).

| جدول/ستون قبلی | وضعیت |
|---|---|
| `people`, `invoices`, `invoice_items`, `payments`, `cost_centers`, `settings` | ✅ کاملاً دست‌نخورده |
| شناسه‌ها (AUTOINCREMENT) | ✅ تغییر نمی‌کنند |
| رکوردهای مشتری (۱۰۰۰ فاکتور / ۵۰۰ پرداخت / ۳۰۰۰ شخص / ۵۰۰۰ کالا) | ✅ حفظ کامل |
| DROP / TRUNCATE / حذف ستون | ❌ هیچ‌کجا وجود ندارد |

- مهاجرت **Idempotent** است (اجرای مجدد بی‌خطر است) و در هر بار اجرای برنامه به‌صورت خودکار چک می‌شود.
- **روش Upgrade:** کافی است برنامه جدید باز شود — مهاجرت خودکار روی همان دیتابیس قبلی اجرا می‌شود.
  هیچ نصب مجدد، حذف دیتابیس یا Import مجدد لازم نیست.

## ۲. محل و ساختار ذخیره فایل‌های پیوست

- مسیر ریشه از **تنظیمات ← «محل ذخیره اسناد اسکن شده»** خوانده می‌شود (`documents_path`).
- اگر مسیر تعیین نشده باشد، الصاق پیوست با پیام خطای واضح رد می‌شود و فاکتور/پرداخت
  **ناقص ذخیره نمی‌شود** (فایل موقت پاک شده و تراکنش Rollback می‌شود).
- ساختار پوشه‌ها با **شناسه یکتای شخص** ترکیب شده است (نه فقط نام):

```text
[مسیر تنظیم‌شده]
    └── [PersonId]_[نام امن شخص]
          ├── فاکتور رسمی_1715..._a3f9.pdf   ← نام اصلی + Timestamp + تصادفی (بدون overwrite)
          └── رسید بانکی_..._.jpg
```

- نام اصلی فایل در ستون `original_file_name` و نام ذخیره‌شده در `stored_file_name` نگه داشته می‌شود.
- نام فایل‌ها از کاراکترهای غیرمجاز ویندوز (`<>:"/\|?*`) پاک‌سازی می‌شوند.

## ۳. پیوست فاکتور و پرداخت

- فرم فاکتور و فرم تراکنش (دریافت/پرداخت): دکمه **«الصاق پیوست»** + فایل‌پیکر سیستم
  (در نسخه دسکتاپ از دیالوگ Electron و در حالت مرورگر از فایل‌پیکر مرورگر با محدودیت ۲۰ مگابایت).
- پس از انتخاب، دکمه **«مشاهده پیوست»** ظاهر می‌شود.
- **مشاهده بر اساس حالت:**
  - پیوستِ تازه انتخاب‌شده و **هنوز ذخیره‌نشده** → فایل مستقیماً از محل اصلی روی سیستم کاربر باز
    می‌شود (Electron: همان مسیر — مرورگر: blob URL محلی). نیازی به ذخیره قبلی نیست.
  - پیوست **ذخیره‌شده** → فایل از محل ذخیره‌سازی اسناد باز می‌شود.
  - اگر هر دو باشند (پیوست ذخیره‌شده + فایل تازه انتخاب‌شده) فایل تازه اولویت دارد.
- در ذخیره: فایل به پوشه شخص Copy و Metadata در همان تراکنش دیتابیس ثبت می‌شود
  (اگر ثبت دیتابیس خطا بدهد، فایل کپی‌شده حذف و تراکنش Rollback می‌شود). فایل اصلی کاربر
  هرگز حذف یا تغییر نمی‌کند — فقط کپی می‌شود.
- **جایگزینی پیوست:** اگر رکورد از قبل پیوست ذخیره‌شده داشته باشد و کاربر فایل جدیدی الصاق کند،
  هنگام ذخیره، رکورد و فایل قبلی حذف و پیوست جدید جایگزین می‌شود (حذف فایل قدیمی فقط بعد از
  COMMIT موفق انجام می‌شود). اگر پیوست جدیدی الصاق نشود، پیوست قبلی حفظ می‌شود.
- **حالت Electron (دسکتاپ):** خود فایل انتخابی کاربر مستقیماً منبع کپی است — بدون کپی میانی اضافی.
  اگر فایل انتخابی بین انتخاب و ذخیره جابجا/حذف شده باشد، ذخیره با پیام واضح رد می‌شود.
- نمایش پیوست در: فرم ویرایش، مودال مشاهده فاکتور، لیست فاکتورها، لیست پرداخت‌ها
  و منوی راست‌کلیک — دکمه فقط وقتی پیوست وجود دارد نشان داده می‌شود.
- **حذف پیوست با تأیید:** دکمه حذف (🗑) در فیلد پیوست فرم‌ها، مودال مشاهده فاکتور و
  منوی راست‌کلیک فاکتور/پرداخت. با دیالوگ تأیید («پیوست … و فایل آن از دیسک برای همیشه
  حذف می‌شود») — سپس رکورد دیتابیس و فایل فیزیکی هر دو حذف می‌شوند. پیوستِ تازه
  انتخاب‌شده اما هنوز ذخیره‌نشده فقط از فرم پاک می‌شود (فایل اصلی کاربر هرگز حذف نمی‌شود).
  حذف پیوست روی فاکتور/پرداخت اثری ندارد و پس از آن می‌توان پیوست جدید الصاق کرد.
- API: `DELETE /api/attachments/:id` — رکورد + فایل؛ حذف مجدد → ۴۰۴.
- باز کردن فایل همیشه با برنامه پیش‌فرض سیستم‌عامل (`shell.openPath` در Electron،
  `cmd start` بدون شل مستقیم در حالت وب) — **بدون اجرای مستقیم فرمان**.
- فاکتورها/پرداخت‌های قدیمی بدون پیوست: مثل قبل نمایش داده می‌شوند و دکمه‌ای برایشان ظاهر نمی‌شود.

## ۴. واحد واقعی کالا در گزارش‌ها

- منبع واحد، ستون موجود `invoice_items.unit` است (سطح Detail فاکتور — دقیقاً همان چیزی
  که هنگام ثبت ذخیره شده). **ساختار موازی جدیدی ساخته نشد.**
- سرور برای هر ردیف فاکتور در گزارش یکپارچه و تفصیلی فیلد `qty_unit` برمی‌گرداند
  (اولین واحد ثبت‌شده اقلام آن فاکتور).
- هر ۶ محل گزارش که قبلاً «عدد» ثابت چاپ می‌کردند اصلاح شدند:
  گزارش تفصیلی شخص (جدول + چاپ + CSV) و گزارش مراکز هزینه (جدول + چاپ + CSV).
- اگر واحدی خالی باشد، برای سازگاری با داده‌های قدیمی «عدد» به‌عنوان Fallback نشان داده می‌شود.

## ۵. خروجی Excel با Template رسمی

- Template رسمی (`work-form.xlsx` — فرم صورتحساب فروش با شیت مخفی «عدد به حروف»)
  در `server/templates/work-form.xlsx` قرار دارد و **همان فایل اصلی، دست‌نخورده** است.
- دکمه **«ارسال به اکسل»** در فرم ویرایش فاکتور و در هر ردیف لیست فاکتورها.
- روش: هر بار یک **Copy** از Template ساخته و فقط `sheet1.xml` (ردیف‌های کالا و مشخصات)،
  `sheet2.xml` (ارجاع جمع کل) و `calcChain.xml` (حذف — خود Excel بازسازی می‌کند) ویرایش می‌شود؛
  Style، Font، Border، Merge (۳۱ مورد)، Row Height، Column Width، Drawing و همه‌جزئیات دیگر
  بایت‌به‌بایت حفظ می‌شوند. بدون وابستگی جدید.

### Mapping (مطابق سند)

| سلول | محتوا | منبع |
|---|---|---|
| D3 / I3 / L3 | نام، شماره ملی، کد اقتصادی فروشنده | فاکتور خرید: طرف حساب — فاکتور فروش: اطلاعات شرکت در تنظیمات |
| C4 / I4 / L4 | آدرس، کد پستی، تلفن فروشنده | همان بالا |
| D6 / I6 / L6 | نام، شماره ملی، کد اقتصادی خریدار | فاکتور فروش: طرف حساب — فاکتور خرید: اطلاعات شرکت |
| C7 / I7 / L7 | آدرس، کد پستی، تلفن خریدار | همان بالا |
| L1 | تاریخ فاکتور با فرمت شمسی دارای اسلش (مثال: `1404/05/12`) | `invoice_date` (۸ رقمی → فرمت‌دار) |
| ردیف 11 به بعد | B=نام کالا، G=مقدار، H=واحد واقعی، I=مبلغ واحد، K=مالیات | اقلام فاکتور |

- ردیف جمع: اگر فاکتور ۱ قلم داشته باشد همان ردیف ۱۲ می‌ماند؛ برای n قلم، n ردیف کالا
  عیناً از روی Contract ردیف ۱۱ Template ساخته می‌شوند (Style/Font/Border/Height بایت‌به‌بایت) و
  **ردیف‌های ۱۲ به بعد Template (ردیف جمع، مبلغ به حروف، امضاها) دقیقاً به تعداد کالاها شیفت می‌شوند**
  — مثل Insert Row خود Excel. Mergeها (B:F هر ردیف کالا و بقیه)، anchor اشیاء Drawing،
  dimension شیت و فرمول‌های `SUM($J$11:J…)`، `SUM($K$11:K…)`، `SUM($L$11:L…)` به محدوده جدید
  به‌روزرسانی می‌شوند؛ فرمول‌های هر ردیف کالا (`I{r}*G{r}`، `J{r}+K{r}`) نیز متناسب با شماره ردیف تولید می‌شوند.
- **محاسبات هر دو شیت:** `fullCalcOnLoad="1"` در workbook تنظیم می‌شود تا Excel هنگام باز کردن،
  همه فرمول‌ها (شامل شیت عدد به حروف) بازمحاسبه کند. مقدار cache فرمول‌ها نیز پیش‌محاسبه درج می‌شود.
- **بدون پیغام Repair:** سلول‌های متنی (نام کالا، واحد، مشخصات، تاریخ) با اتریبیوت استاندارد
  `t="inlineStr"` درج می‌شوند؛ خروجی با XML Parser سیستم و بررسی سلول‌به‌سلول اعتبارسنجی شده و
  بدون هیچ پیغام بازسازی/ترمیم مستقیم باز می‌شود.
- استخراج Template کاملاً درون‌پردازه‌ای است (خواندن ZIP از Central Directory با zlib داخلی Node) —
  هیچ child process مضاف (PowerShell) اجرا نمی‌شود؛ exportها سری‌سازی شده‌اند (صف داخلی) تا
  exportهای پشت‌سرهم هم بی‌خطر باشند.
- فایل خروجی در پوشه Temp ساخته و با Excel پیش‌فرض باز می‌شود؛ Template هرگز Overwrite نمی‌شود.
- خطاها (Template نبودن/خراب، اطلاعات ناقص) پیام واضح دارند و برنامه Crash نمی‌کند.
- `GET /api/invoices/:id/excel` هم فایل را برای دانلود مستقیم تولید می‌کند (بدون باز کردن).

## ۶. تنظیمات

- کارت جدید **«محل ذخیره اسناد اسکن شده»** با دکمه **«انتخاب پوشه»** (Folder Browser سیستم).
- اعتبارسنجی هنگام ذخیره تنظیمات: ساخت پوشه، تست نوشتن، رد مسیر غیرقابل‌دسترس با پیام خطا.
- همچنین باگ موجود ناسازگاری `electronAPI/hesabAPI` در انتخاب پوشه پشتیبان اصلاح شد
  (هر دو نام پشتیبانی می‌شوند — Backward Compatible).

## ۸. Rollback

1. برنامه جدید بسته شود؛ برنامه قبلی (نسخه قبل) باز شود — همه چیز مثل قبل کار می‌کند
   چون هیچ ساختار یا داده قبلی تغییر نکرده است.
2. در صورت تمایل جدول `attachments` و ردیف `documents_path` را می‌توان بدون هیچ اثری حذف کرد
   (سایر اجزا به آن وابستگی کلیدی ندارند):
   ```sql
   DROP TABLE attachments;   -- فقط فایل‌های یتیم را قبلش از پوشه اسناد انتقال/حذف کنید
   DELETE FROM settings WHERE key='documents_path';
   ```
3. پشتیبان: قبل از هر آپgrade، از پنل تنظیمات «پشتیبان‌گیری همین حالا» را بزنید
   (دیتابیس SQLite در `data/hesab.db` یا `%APPDATA%/Hesab` نسخه دسکتاپ).
   Backup خودکار موجود نیز فعال بماند.

## ۹. تست‌های انجام‌شده (خلاصه نتایج)

**مهاجرت (روی کپی دیتابیس با اسکیمای قدیمی):** تعداد رکوردها/IDها/تنظیمات حفظ شد؛
جدول جدید ساخته شد؛ اجرای مجدد امن. — `ALL PASS`

**خروجی اکسل (۱/۲/۵ کالا):** ۵۴ بررسی — ZIP/XML معتبر (اعتبارسنجی با XML Parser سیستم)،
فرمول‌های `I*G`، `J+K`، `SUM` ردیف جمع متناسب ردیف‌ها، حفظ ۳۱ Merge، Drawing،
واحد واقعی، مشخصات فروشنده/خریدار به‌صورت Text (حفظ صفر ابتدایی کد ملی)،
calcChain حذف و Template اصلی دست‌نخورده. — `ALL PASS`

**Regression انبوه (شبیه‌سازی مشتری):** ۳۰۰ شخص، ۱۰۰۰ فاکتور، ۵۰۰ پرداخت؛
لیست‌ها/گزارش‌ها/مانده‌ها/ویرایش/حذف/آمار؛ ۸ واحد مختلف در گزارش با `qty_unit` صحیح؛
پیوست در ویرایش فاکتور؛ خروجی اکسل. — `ALL PASS`

**یکپارچگی پیوست (۲۷ بررسی):** rollback بدون مسیر، رد مسیر غیرقابل‌دسترس،
ساختار پوشه `PersonId_نام`، حفظ نام اصلی، محتوای فایل صحیح، پیوست پرداخت. — `ALL PASS`

**حذف پیوست (۱۸ بررسی):** حذف رکورد + فایل فیزیکی برای فاکتور و پرداخت،
سلامت ماندن رکورد اصلی و `attachment_count=0`، حذف مجدد → ۴۰۴، بدون فایل یتیم،
افزودن مجدد پیوست پس از حذف. — `ALL PASS`
(تست UI: دیالوگ تأیید، پاک شدن فیلد فرم و حذف دکمه‌ها از لیست پس از حذف.)

> `test-migration.cjs`, `test-regression.cjs`) با دستور
> `node <script>` قابل اجرا هستند.
